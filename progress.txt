2. High-Level Data Flow Matrices


Scenario A: Founder / Owner Onboarding Path

1. User Sign Up: Lands on /register via RegisterGateway. Inputs name, email, and leaves the token string container empty.
2. Context Assignment: The system initializes an implicit role: "owner" evaluation and writes profile parameters into local storage.
3. Route Security Layer Check: The route enforcer shield interceptor detects user.role === "owner" with branches.length === 0.
4. Target Allocation: Pushes history states straight to /branches to force infrastructural layout provisioning.

Scenario B: Clerk / Operations Operator Path

1. User Sign Up: Accesses /register. Submits baseline details alongside a verified manager token (e.g., AMHL-EMP-92).
2. Context Assignment: The context matches the token against system indexes, assigns role: "worker", and links their user profile to that explicit assignedBranchId.
3. Route Security Layer Check: The route shield approves authorization fields.
4. Target Allocation: Bypasses configuration grids and forces routing parameters directly to /dashboard.

5. Technical Advantages of This Architecture

• Single Network Footprint: Since every widget reads from the centralized AppContext, we avoid parallel or mismatched state calls. The application is completely fast, predictable, and clean.
• Backend Hook Ready: Replacing browser storage with live Cloud APIs, Supabase tables, or Prisma backends is a cinch. We only change inside the AppContext.tsx file—the entire dashboard, forms, buttons, and mobile UI won't require a single code alteration.
• Enforced Operational Sandboxing: Access modifiers ensure workers never slip into system diagnostics views, settings blocks, or adjacent branch queues by accident, isolating data cleanly.
